sia-policy-automation · briefing for CyberArk / Idira engineers

SIA Onboarding Flow

One set of objects per server, created from a spreadsheet: for every Windows server its own strong account (its local administrator, referenced from the Vault), its own target set, and an access policy named after the server for the Identity role (or group) that may use it — a second row gives a second principal its own policy. For Linux servers only the policy (SIA uses an SSH certificate there). Run it again and it changes nothing; change a list and it shows you the difference before touching anything; stop it half-way and it resumes.

The one idea to get first

In SIA, the strong account is not a setting on the policy. Three separate objects do the work, and the server's FQDN is the key that joins them at connection time. The tool creates the three amber objects below, one set per server; everything dashed must already exist (the local admin account in the Vault can be onboarded by the optional vault stage).

Access policy

Who may connect (an Identity role, or a group), to which FQDN, how (RDP with an ephemeral local user in chosen local groups) and when. Named after the server; a second principal gets a second policy (-ops).

web01.corp.example.com

Target set

Type Target, named exactly the server FQDN, pointing at a strong account. This is how SIA knows which account to use for that server.

web01.corp.example.com

Strong account

SIA's "VM secret": a reference to the server's own local administrator account in the Vault, derived from one naming rule (safe, account name, user name). Must be local admin on the target.

web01-Administrator_SIA-LocalAdmins

Linux servers need only the access policy: SIA's Linux ZSP hands the user a short-lived SSH certificate, so there is no strong account and no target set for them (rows marked protocol = ssh).

What SIA does when someone connects

The tool is not in this path. It sets up the objects the path relies on, and connect-info writes down what the user needs.

  1. The user picks web01.corp.example.com in the portal (Access › Infrastructure › Connect › RDP) or an RDP client

    Nothing is typed: no user name, no password. From an RDP client the gateway is <subdomain>.rdp.cyberark.cloud and the user name is the connection string secureaccess /i alice@acme.cyberark.cloud /s acme /a web01.corp.example.com. Their Identity session says who they are and which roles and groups they hold.

  2. SIA looks for a policy that matches

    Role (or group) ∈ principals, FQDN matches the rule, current time inside the access window. Users pick the server; the policy named after it is what applies.

  3. SIA finds the target set named web01.corp.example.com

    The target set's secret_id says which strong account to use. Without a target set the policy is valid but the connection cannot be provisioned.

  4. The connector uses the strong account

    Over WinRM it creates a temporary local user named after the connecting user — the first 7 characters of the login plus a random string, 20 characters in all (alice.sXk3f9Qm2dLp7bR) — and adds it to the local groups the policy names (e.g. Administrators). The strong account's password comes from the Vault.

  5. Session runs, then the temporary user is removed

    The session ends after the policy's maximum length (2 h by default) or idle time (10 min), with a 30-second warning; the temporary user and its profile are deleted. Reconnecting means a new temporary user (enable_reconnect = false). Zero standing privileges: nothing is left on the box afterwards.

Principal names are turned into what a UAP policy actually needs — a role's ID (roles are the default), or a group's ID plus the directory it came from — by asking Identity's directory service. Passwords are never in a CSV: they come from a protected password file, environment variables or a prompt, and are redacted from every log and error.

How a run flows

  1. Read and check the lists

    Every problem is reported with file and line (bad FQDN, unknown strong account, duplicate policy name…). If anything is wrong, nothing else happens.

  2. Sign in and read what the tenant already has — for this wave only

    The service user gets a platform token. Up to 2,000 servers the tool reads per server (one search each, in parallel); above that it reads one listing of the policies it manages. Rows already finished according to the checkpoint are not read at all (--resume).

    Identity, SIA (dpa) and UAP APIs — all read-only at this point.

  3. Turn names into IDs

    Each principal name becomes a role ID (or a group ID plus its source directory). Each strong-account name is matched to a secret.

  4. Compare desired with actual, per server

    Every object ends up as create exists drift or blocked. plan stops here and prints the table.

  5. Apply in dependency order

    Vault accounts (optional), then strong accounts, then target sets (batches of 50), then policies — each policy is read back to confirm the requested Active or Suspended state, and only complete verified rows go into the checkpoint. A report (table, JSON, CSV) is written.

    A server whose strong account or target set failed has its policies blocked, never created half-way. The first object of each stage is created alone; only then do the workers fan out.

Why it is safe to run twice

  • Dry run first. plan changes nothing; apply shows the plan again and asks you to type yes.
  • Idempotent. Objects are matched by name, so a second run reports exists everywhere and creates nothing. A create that failed uncertainly (timeout, 5xx) is never blindly re-sent — the next run simply finds the object if it landed.
  • It never deletes. A server removed from the CSV is left alone in SIA.
  • Drift is reported, not silently fixed. If someone changed a policy in the UI, you see drift. Fixing it needs --update, and only works on objects the tool created — they carry the tag sia-policy-automation — or ones you explicitly --adopt.
  • Fails fast. The first 4xx from a create (a payload or permission problem that would repeat for every row) stops the run; the rest is reported as blocked, not sprayed with 200 identical errors.
  • Renames survive. A tool-created policy renamed in the UI is still recognised by its tag and FQDN rule, and reported as drift instead of being duplicated.

What you actually type

python sia_onboard.py preflight                       # auth OK? which API paths? self-hosted PAM configured? counts
python sia_onboard.py show-policy "Ref-web09"           # dump a policy you made by hand → confirm the FQDN/principal encoding
python sia_onboard.py plan  --input input               # dry run: the create / exists / drift table
python sia_onboard.py apply --input input --workers 8   # do it (asks for "yes"); --resume continues an interrupted run
python sia_onboard.py verify --input input              # PASS / MISSING / FAIL per row, for sign-off
python sia_onboard.py connect-info --input input --rdp-dir out   # gateway, user name and .rdp file per server

First time on a tenant: create one policy for one server by hand, run show-policy on it, then plan and apply with a one-server CSV. Test the RDP login as a member of the role (watch the temporary user appear and disappear), run verify, re-run apply (everything must say exists), then load the real lists in waves of a few thousand.

Questions engineers usually ask

Why isn't the strong account on the policy?
That is SIA's model, not the tool's: policies decide who and where; target sets decide with what account. Here every server has one of each, joined by the FQDN.
Why does my vault strong account show up as web01-Administrator_SIA-LocalAdmins?
SIA generates that name (<account>_<safe>) for vault-referenced accounts and rejects custom names. The tool uses the same name so lookups are deterministic.
What if the policy already exists?
It is compared, not recreated. Same principals, same FQDN rule → exists; suspended or in error → inactive. Anything else → drift, with the difference spelled out. A same-name policy made by hand is compared too (SIA refuses the duplicate name) and reported as unmanaged.
Why did it refuse to update something with --update?
Because the object has no owner tag — someone made it by hand. Add --adopt <fqdn> to take ownership; the update then also tags it.
How does a run of 70,000 servers stay manageable?
Waves (--offset/--limit or one CSV per wave), per-server lookups instead of reading the whole tenant, a checkpoint that --resume skips, a shared request-rate budget for the workers, progress lines every 100 objects, and verify after each wave.
What does it not do?
Domain ephemeral users, creating the Windows accounts themselves, deleting anything, and changing tenant settings. Those are deliberate boundaries for this version; Linux/SSH rows are supported (policy only).
Payload shapes follow the documented Access Control Policies, SIA strong-account/target-set and PVWA APIs and CyberArk's official SDKs. Conventions are confirmed per tenant with preflight and show-policy before bulk runs: the API path families, the FQDN-rule encoding, the principal shape (ROLE by default; source-directory fields optional for roles) and the fields the policy list carries.
