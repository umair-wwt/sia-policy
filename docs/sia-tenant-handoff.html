01

Service user

Owner: Identity administrator

One non-interactive Identity user. The automation authenticates as this user for every call it makes — to SIA, to the policy service, and to Identity itself.

1.1

Create the Identity user

A service account, not a person. Password should not expire and the user must be exempt from MFA — the tool runs unattended and cannot answer a challenge.

SIA_CLIENT_ID
1.2

Tick Is OAuth confidential client

This flag is what enables POST /oauth2/platformtoken with a client-credentials grant. Without it, authentication fails at the first call with HTTP 400/401 and nothing else can be tested.

1.3

Add to the Secure Infrastructure Access administrator role

Internally named DpaAdmin. Grants the strong-account, target-set and policy permissions below. Without it, authentication succeeds but every read returns HTTP 403.

1.4

Confirm the user can query directories

Group-to-principal resolution calls GET Core/GetDirectoryServices and POST UserMgmt/DirectoryServiceQuery on the Identity tenant. This is a separate permission from the SIA role and is the most common 403 in practice.

If Identity rejects the platform token, there is a documented fallback — the tool can switch to the service-user OIDC flow instead. Just tell us which one works; no extra setup either way.

Permissions the user actually exercises: read/create strong accounts (/api/secrets), read/create/update target sets (/api/targetsets), read/create/update access policies (/api/policies), read tenant settings (/api/settings, optional — the tool degrades gracefully on 403), and the two Identity directory calls above. It never deletes anything.

02

Tenant URLs

Owner: CyberArk engineer · 2 values

Two strings. Everything else is derived from them.

2.1

Tenant subdomain

Lowercase, the bare subdomain only — acme, not the full URL. The tool derives acme.dpa.cyberark.cloud (SIA), acme.uap.cyberark.cloud (policies) and acme.rdp.cyberark.cloud (the RDP gateway) from it.

subdomain
2.2

Identity tenant URL

From Identity Administration › Settings › Customization › Tenant URLs — the https://abc1234.id.cyberark.cloud form. No trailing slash. The tenant alias https://acme.cyberark.cloud also works if the ID form is awkward to obtain.

identity_url
03

Identity groups

Owner: Identity administrator

Each generated policy grants access to one Identity group. The groups must exist first — the tool looks them up by name and fails the row if the name does not resolve to exactly one group.

3.1

Create or confirm each group, and send the exact names

Matching is on SystemName or DisplayName, so a near-miss like SIA_Web_Admins versus SIA-Web-Admins fails. Exact spelling matters more than anything else on this page.

group
3.2

Flag any name that exists in more than one directory

If the same group name lives in both Cloud Directory and AD, the lookup is ambiguous and the row fails. Tell us the directory to pin for those names — everything else is found by name alone.

groups.csv

Each group must resolve to a row carrying InternalName, DirectoryServiceUuid and ServiceInstanceLocalized — these become the policy's principal. A group that exists but returns an incomplete row cannot be used.

04

Vault accounts and the naming convention

Owner: Vault administrator

The design is one strong account per server — each server's own local administrator, referenced from the Vault. This is usually the longest-lead item, because it is per-server rather than per-tenant.

4.1

Name the Safe holding the local administrator accounts

One Safe for all of them, e.g. SIA-LocalAdmins. The service user needs no direct Vault access — SIA holds only a reference and the CPM rotates the password.

safe_template
4.2

Confirm the account naming rule inside that Safe

The tool derives each account name from the hostname, e.g. <hostname>-Administrator. Tell us the real convention — if accounts are named differently, the template changes rather than the accounts.

account_name_template
4.3

Confirm the Windows user name on those accounts

Typically Administrator. This is the local Windows account SIA logs on with, distinct from its name in the Vault.

username_template
4.4

Tell us how many servers already have their account in the Vault

A server whose account is missing fails that row. Two ways forward: onboard them in the Vault first, or let the tool onboard the missing ones through the PVWA REST API (§8), which needs each account's current password supplied to it.

Naming note: SIA generates the reference name as <account_name>_<safe> — e.g. web01-Administrator_SIA-LocalAdmins — and rejects custom names. The tool matches that format deliberately, so it always finds the right reference on re-runs.

05

PAM integration and connectors

Owner: CyberArk engineer · PAM Self-Hosted 14.4+

SIA has to know which Vault to read strong-account passwords from, and needs connectors that can reach the servers. Neither is created by the tool; both are read back by preflight.

5.1

Complete the PAM Self-Hosted integration in SIA settings

The tool reads GET /api/settings and checks four fields on self_hosted_pam: tenant_type (must be SELF_HOSTED, not PCLOUD), pvwa_base_url, connector_pool_id and service_user_secret_id. Any missing field is reported as incomplete.

5.2

Confirm connectors are deployed and reach the target servers

The connector opens WinRM to each Windows server to create and remove the temporary user. This is a connection-time dependency, not an onboarding one — policies will be created successfully and then fail to connect if it is missing.

06

One reference policy, built by hand

Owner: CyberArk engineer · returns a JSON export

The single most valuable thing on this page. Tenants encode a few policy details differently, and this is how we confirm the generated policies will match yours before creating thousands of them.

6.1

Create one zero-standing-privilege VM policy in the portal, by hand

For one server, looking exactly the way you want every generated policy to look: the right access window, session limits, and RDP connection profile. Then send us its name.

6.2

We export and compare it

We run show-policy against it and check three things: how targets.fqdnRules encodes the server (we expect operator EXACTLY, the full FQDN in computernamePattern, the DNS domain in domain), what sourceDirectoryId and sourceDirectoryName your principals carry, and which fields the list endpoint returns.

This policy can also be reused as a live template — every generated policy then clones its access window, session settings and connection profile, so those stay maintained in one place in the portal rather than in our config file.

07

Server and network prerequisites

Owner: Windows / GPO and network teams

Not the CyberArk engineer's work, but worth forwarding in the same thread — these block connections, not onboarding, so they surface late and painfully if missed.

7.1

WinRM reachable from the connectors

TCP 5985 (HTTP) or 5986 (HTTPS). If certificates are valid on the targets, say so — we can turn on certificate validation for the target sets rather than leaving it off.

7.2

LocalAccountTokenFilterPolicy = 1 via GPO

Local accounts cannot be used remotely without it. Push it before the first connection test, not after.

7.3

Local admin account state on each server

In the local Administrators group, marked Account is sensitive and cannot be delegated, and not a member of Protected Users.

7.4

Exclude domain controllers from the server list

SIA does not support RDP to domain controllers. If any are in scope, they need a different access path and should be filtered out of the inventory before we build the CSV.

08

Optional — PVWA onboarding stage

Owner: Vault administrator · only if 4.4 found gaps

Skip this entirely if every local admin account is already in the Vault. It exists so the tool can onboard the missing ones itself instead of blocking the rollout.

8.1

PVWA base URL and authentication method

The https:// URL of the PAM Self-Hosted PVWA, and whether logon is CyberArk or LDAP.

[pvwa]
8.2

A PVWA user permitted to add accounts to the Safe

Separate from the SIA service user. Add-account permission on the target Safe only — nothing broader is used.

PVWA_USER
8.3

Confirm the platform ID for onboarded accounts

The tool defaults to WinServerLocal. If your platform differs, or mandates extra required properties on new accounts, we need to know before the first onboarding run.

platform_id

This stage also needs each account's current password supplied to the tool so it can hand it to the Vault. With every account already vaulted, no password ever passes through the tooling at all — which is the strong reason to prefer pre-onboarding where it is feasible.

Open questions for CyberArk

Answers wanted before the large waves, not before the first server

These do not block a pilot. They do determine how fast we can go afterwards, and no published answer was found in the documentation.

Q1

Are there limits on object counts per tenant?

Specifically the number of access policies, target sets and strong accounts. The programme is sized at 70,000–140,000 policies, which is well beyond anything documented.

Q2

What are the API rate limits?

The tool has a shared rate limiter and parallel workers, both configurable. We would rather set them from a published number than discover the limit by tripping it.

Q3

What does a user see when two policies match the same user and server?

Servers with a second group get a second policy. We want to confirm the portal behaviour before that pattern is used at scale.

Q4

Does the policy list endpoint return principals?

Answered by the export in §6. If it does, re-runs over finished servers cost a fraction of the requests — this is the difference between a cheap weekly reconcile and an expensive one.

What happens once §1 and §2 come back: we run preflight, which authenticates, detects which API variants this tenant serves, and prints the tenant's current strong-account, target-set and policy counts. It is entirely read-only. Every line should say OK — anything that does not comes straight back to you with the exact error.

The first real run is one server, verified end to end with a live RDP login, before any list is loaded.
